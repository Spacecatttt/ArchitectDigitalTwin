# ADR-0004. Вибір платформи цифрового двійника: Eclipse Ditto

## Статус

Прийнято, 2026-10-26

## Контекст

У ЛР 1 спроєктовано службу синхронізації стану (`SyncService`), Twin API (`TwinApi`) і інформаційну модель (`InfoModel`), але не обрано продукт, що їх реалізує. Вимоги до продукту випливають з рішень ЛР 1: виробничі дані не виходять за периметр підприємства (ADR-0001), телеметрія надходить через MQTT від граничного шлюзу (ADR-0002), потрібна валідація стану за моделлю (FR-07), потік змін для подання без опитування (гіпотеза Г-01), масштаб — до 10 верстатів (NFR-03), затримка синхронізації p95 ≤ 200 мс (NFR-01).

Порівняльна оцінка з вагами, заданими до огляду платформ, — у `docs/platform.md`, розділ «Порівняння платформ».

## Варіанти

1. **Eclipse Ditto 3.9** — відкрита (EPL-2.0), моделі W3C WoT TM з валідацією, з’єднання MQTT з JavaScript-відображенням, події SSE/WebSocket, локальне розгортання. S = 4,60.
2. **Eclipse BaSyx (AAS)** — відкрита, стандарт AAS для Industrie 4.0, локальна. Але приймання MQTT лише через окремий DataBridge, менша спільнота. S = 4,05.
3. **FIWARE Orion-LD (NGSI-LD)** — відкрита, локальна, масштабована. Але AGPL-3.0, MQTT лише через IoT Agents (додаткова ланка в маршруті й у затримці), модель — NGSI-LD без вбудованої валідації за типом. S = 4,05.
4. **Azure Digital Twins** — керована хмара, DTDL, найкраща масштабованість. Але немає локального розгортання (суперечить ADR-0001), телеметрія — через IoT Hub і функції, оплата за операції. S = 2,60.

## Рішення

Обрано **варіант 1 — Eclipse Ditto 3.9.7**. Конкретне втілення блоків моделі ЛР 1:

| Блок ЛР 1 | Втілення на стенді ЛР 2 |
|---|---|
| `TelemetryBroker` | Eclipse Mosquitto 2 |
| `DataQuality` (частково) + `InfoModel` | валідація змін Ditto за моделями WoT TM `twin/*.tm.jsonld`; відображення `platform/mapping.js` |
| `SyncService` | Ditto (`things`, `policies`, `connectivity`) |
| `TwinApi` | HTTP API Ditto + SSE через проксі `web` (лише читання) |
| `TimeSeriesStore` | історик `sync/historian.py` + InfluxDB 2.9 (на стенді замість TimescaleDB з ADR-0001, див. наслідки) |
| `SecurityService` (частково) | політики Ditto: суб’єкт з’єднання `integration:telemetry` має лише `WRITE` на `thing:/features` |
| `OperatorUi` | `ui/index.html`, Grafana |

Рішення спирається на розрахунок: S = 4,60 проти 4,05 у найближчих альтернатив, а перевірка з рівними вагами дає той самий результат (4,50 проти 4,00).

## Наслідки

- (+) Модель типу (WoT TM) — стандарт W3C; її можна перенести на іншу платформу, а онтологія `twin/ontology.ttl` пов’язана з нею через `@type`.
- (+) Платформа сама відхиляє невалідні зміни — перший рубіж якості даних (FR-07) без власного коду.
- (+) SSE дає push-оновлення подання — основу перевірки гіпотези Г-01 у ЛР 4.
- (−) Ditto вимагає 4–6 ГБ пам’яті й MongoDB; для одного верстата це важче, ніж власна служба синхронізації.
- (−) Ditto не зберігає історію значень: потрібен окремий історик і сховище часових рядів. На стенді це InfluxDB (так задано інструкцією ЛР 2); ADR-0001 (TimescaleDB) лишається чинним для виробничого розгортання, а вибір між ними — питання ЛР 4.
- (−) Оновлення одного двійника Ditto обробляє послідовно, тож пропускна здатність для одного верстата обмежена (вимірюється на занятті 4); горизонтальне масштабування розподіляє між вузлами лише різні двійники.
- (−) Ризик залежності від проєкту з невеликою кількістю основних розробників; пом’якшується тим, що модель (WoT TM) і з’єднання (MQTT) — стандартні.
