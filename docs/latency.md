# Модель інформаційних процесів і наскрізна затримка

Діаграма маршруту — `diagrams/dataflow.mmd` (`dataflow.svg`). Розглядаємо критичний для оператора маршрут: відлік навантаження шпинделя або блок вібрації → ознака автоколивань → стан двійника → веб-панель. Саме за цим маршрутом оператор має вчасно побачити небезпечний режим (FR-03, FR-04).

## 1. Послідовні ділянки

| № | Ділянка | Перетворення | Затримка, мс | Обґрунтування оцінки |
|---|---|---|---|---|
| L1 | ЧПК/датчик → шлюз | оцифрування (DAQ) або OPC UA-підписка: інтервал вибірки 40 мс, інтервал публікації 50 мс | 40 | середнє очікування ≈ половина інтервалу публікації (25 мс) + обробка сервера ЧПК (≈ 15 мс); [S5] вимірював 55–120 мс для ланки ПЛК→OPC UA→модель з додатковим проміжним сервером |
| L2 | Обробка на шлюзі | перевірка відліку, суміжні вікна по 512 відліків (102 мс, без перекриття, ≈ 10 ознак/с), БПФ, 8 ознак, пакування JSON | 60 | часова мітка ознаки — середина вікна, тому ознака «запізнюється» на половину вікна (≈ 51 мс) + обчислення (≈ 5 мс) + серіалізація |
| L3 | Шлюз → брокер | публікація MQTT 5, QoS 1, TLS 1.3, LAN 1 Гбіт/с | 15 | пакет < 1 кБ; TLS-сесія постійна; підтвердження PUBACK |
| L4 | Брокер → платформа | доставка підписнику, позначка якості, оновлення стану двійника в пам’яті | 35 | розбір JSON, перевірка правил, запис у кеш стану |
| L5 | Платформа → інтерфейс | веб-панель опитує REST API кожні 500 мс; HTTP-запит; рендер | 290 | середнє очікування 250 мс + HTTP 15 мс + рендер 25 мс |
| | **РАЗОМ** | | **440** | |

За формулою (4): `L = 40 + 60 + 15 + 35 + 290 = 440 мс`.

## 2. Паралельні гілки (до суми не входять)

| Гілка | Затримка | Чому не входить до суми |
|---|---|---|
| Брокер → TimescaleDB (запис пакетами раз на 1 с) | 500–1000 мс | веб-панель показує поточний стан із кешу служби синхронізації, а не з БД; БД потрібна для трендів та історії |
| Шлюз → архів сирої вібрації (Parquet, файл раз на 10 с, лише під час різання) | ≈ 10 с | архів читає інженер постфактум |
| TimescaleDB → аналітика зносу інструмента (вікно 1 хв) | ≈ 60 с | знос змінюється за хвилини–години; результат потрапляє в стан двійника окремою подією |
| Служба синхронізації → журнал аудиту | ≈ 5 мс | не впливає на відображення |

Якби веб-панель читала поточні значення з TimescaleDB, ділянка запису стала б послідовною, і затримка зросла б на 0,5–1 с — NFR-02 гарантовано не виконувалась би. Тому в архітектурі стан для відображення береться зі служби синхронізації.

## 3. Порівняння з вимогами (середні значення)

| Показник | Ділянки | Значення | Ціль | Результат |
|---|---|---|---|---|
| Затримка синхронізації (NFR-01) | L1 + L2 + L3 + L4 | 40 + 60 + 15 + 35 = **150 мс** | ≤ 200 мс | виконано (запас 25 %) |
| Наскрізна затримка (NFR-02) | L1 … L5 | **440 мс** | ≤ 500 мс | виконано (запас лише 12 %) |

Найбільшу частку (66 %) дає ділянка **«Платформа → інтерфейс»**, а точніше — очікування наступного опитування.

## 4. Дослідження моделі (`latency.py`)

Цілі NFR-01/02 задано для **95-го процентиля**, а сума середніх цього не перевіряє: очікування опитування рівномірно розподілене від 0 до 500 мс, тож у 5 % випадків воно перевищує 475 мс. Тому сценарій, крім формули (4), моделює кожну ділянку випадковою величиною (рівномірний або логнормальний розподіл навколо оцінок таблиці) і проганяє 20 000 відліків методом Монте-Карло; досліджує чутливість до періоду опитування та масштабування до 10–20 верстатів.

Запуск:

```
python3 docs/latency.py
```

### Висновки з дослідження

1. **За середнім базова конфігурація відповідає NFR-02 (440 мс), а за p95 — ні (661 мс).** Висновок «вимогу виконано», зроблений лише з формули (4), був би хибним. Синхронізація (NFR-01) виконується з запасом і за p95 (181 мс ≤ 200 мс).
2. Чутливість: p95 лінійно залежить від періоду опитування T (p95 ≈ 0,95·T + 190 мс); NFR-02 виконується лише за T ≤ ≈ 325 мс (з перевірених значень — 300 мс). Але зменшення періоду множить кількість запитів до API (у 10 верстатів × кілька панелей × 3–10 запитів/с) і не прибирає саму причину — очікування.
3. Масштабування: за прийнятих припущень про зростання навантаження служби синхронізації p95 синхронізації зростає на 6 % для 10 верстатів (NFR-03: ≤ 30 % — виконано), але для 20 верстатів уже 207 мс > 200 мс, тобто NFR-01 стає межею масштабу на одному сервері. Коефіцієнти навантаження — припущення, які перевіряються навантажувальним прогоном у ЛР 2.

## 5. Гіпотеза

**Гіпотеза Г-01.** Заміна періодичного опитування REST API веб-панеллю (період 500 мс) на push-сповіщення через WebSocket від служби синхронізації зменшить медіану наскрізної затримки «датчик — подання» **щонайменше на 40 %** і забезпечить виконання NFR-02 для **p95 ≤ 500 мс** без збільшення навантаження на API.

- **Обґрунтування:** гіпотезу спрямовано на ділянку з найбільшою часткою (66 %); модель дає зменшення медіани на 58 % (435 → 182 мс) і p95 661 → 216 мс; [S2] прямо вказує опитування як обмеження синхронізації.
- **Метрика:** медіана та 95-й процентиль наскрізної затримки (мітка джерела відліку → момент відображення в браузері), мс; додаткова — кількість запитів до API за хвилину.
- **Спосіб перевірки (ЛР 4):** порівняльний прогін двох конфігурацій (опитування 500 мс / WebSocket push) за однакового навантаження — емулятор ЧПК і датчиків відтворює однаковий записаний сеанс різання тривалістю 30 хв; годинники синхронізовано; ≥ 10 000 вимірювань у кожній конфігурації; значимість зсуву розподілів перевіряється критерієм Манна — Вітні (α = 0,05), величина ефекту — за зміною медіани й p95.
- **Критерій підтвердження:** медіана зменшилась ≥ 40 %, p95 конфігурації push ≤ 500 мс, а кількість запитів до API за хвилину не зросла. Якщо гіпотезу підтверджено, найбільшою ділянкою стає L2 (вікно ознак), на яку спрямовується наступна гіпотеза (менше вікно або перекриття 75 %).
